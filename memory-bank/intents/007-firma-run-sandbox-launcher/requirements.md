# Requirements: Firma Run Sandbox Launcher

## Intent Overview

Build `firma-run`, a Linux-first Rust CLI that wraps arbitrary agent processes inside a sandbox backend selected by FIR-60 and enforces structural sidecar routing with fail-closed behavior. FIR-61 implements generic runtime plumbing (`firma run -- <agent-command>`), ships `generic` and `codex` profiles, and provides E2E/benchmark artifacts. Claude Code specialization remains FIR-62 scope.

This intent resolves two open design gaps from FIR-61 review:

1. DNS confinement with bubblewrap must be explicit and structural.
2. Long-running agent capability lifecycle must be defined (not only short-lived session assumptions).

## Business Goals

| Goal | Success Metric | Priority |
|------|----------------|----------|
| Structural governance boundary for agent runtime | Outbound traffic from wrapped agents cannot bypass sidecar policy plane | Must |
| Zero-config developer UX | Fresh user can run `firma run -- python my_agent.py` and see sidecar-audited calls without manual wiring | Must |
| Coverage extension beyond HTTP-native SDK hooks | Shell/subprocess/browser-originated HTTP traffic is mediated by sidecar in E2E tests | Must |
| Security narrative readiness for launch | Benchmark + fail-closed evidence exists in `target/benchmarks/` and docs | Must |
| Extensible backend posture | Linux implementation does not block future Firecracker enterprise profile | Should |

## Functional Requirements

### FR-1: CLI Surface and Invocation Model
- **Description**: Provide `firma run` CLI surface for wrapping arbitrary commands.
- **Acceptance Criteria**:
  - Supports `firma run -- <agent-command> [args...]`
  - Supports `--profile <name>` and defaults to `generic`
  - Supports `--config <path>` for profile/config override
  - Supports `--` passthrough semantics exactly once
- **Priority**: Must

### FR-2: Process Orchestration and Interactive Safety
- **Description**: Wrapper must remain invisible for interactive workflows.
- **Acceptance Criteria**:
  - `stdin/stdout/stderr` are forwarded without buffering artifacts
  - PTY/TUI behavior (cursor control, resize, Ctrl-C) is preserved
  - Exit code returned to caller matches wrapped agent process exit code
- **Priority**: Must

### FR-3: Backend Contract and Linux bwrap Backend
- **Description**: Implement backend interface from FIR-60 with Linux `bwrap` path now and pluggable extension points.
- **Acceptance Criteria**:
  - Backend trait exposes `prepare`, `enforce_network`, `start_agent`, `verify_fail_closed`, `teardown`
  - Linux `bwrap` backend is production path in FIR-61
  - Non-Linux backends return explicit unsupported errors in FIR-61 (no hidden fallback)
  - Backend-specific checks produce actionable startup diagnostics
- **Priority**: Must

### FR-4: Structural Outbound Routing (No Trust in Cooperative Proxy)
- **Description**: Outbound network control must be structural, not dependent on agent cooperation.
- **Acceptance Criteria**:
  - Agent runs in isolated network namespace (`bwrap --unshare-net` or equivalent backend primitive)
  - Sandbox has no direct external egress path; sidecar path is the only allowed route
  - If proxy env vars are ignored, direct external network still fails (fail-closed)
  - Shell-originated HTTP (`curl`, `wget`) from inside sandbox is mediated by sidecar or blocked (never direct)
- **Priority**: Must

### FR-5: DNS Confinement (Explicit Implementation)
- **Description**: DNS must not leak to host resolver from sandbox.
- **Acceptance Criteria**:
  - Sandbox `/etc/resolv.conf` is generated by `firma-run` and does not point to host resolver config
  - DNS queries are forced to a sandbox-local DNS stub
  - DNS stub forwards via Firma-controlled path (sidecar-mediated channel) and does not use host ambient resolver directly
  - Direct DNS to arbitrary resolvers is blocked by sandbox network confinement
- **Priority**: Must

### FR-6: Sidecar Routing Bridge and Identity Injection
- **Description**: Every mediated request carries deterministic runtime identity for attribution.
- **Acceptance Criteria**:
  - Per-run deterministic `sandbox_id` is generated and logged
  - Wrapper injects attribution headers/claims (at minimum: `sandbox_id`, `session_id`, `profile`)
  - Sidecar audit entries can distinguish concurrent `firma-run` instances
  - Identity propagation is deterministic across retries/restarts within the same run instance
- **Priority**: Must

### FR-7: Config Schema and Policy Knobs
- **Description**: Support profile-based runtime config for sandbox behavior.
- **Acceptance Criteria**:
  - Config supports profile defaults plus user overrides
  - Config includes allowed domains, mounts, env passthrough, sidecar endpoint
  - Config parser validates unknown/invalid fields fail-fast
  - Effective config can be rendered for debugging
- **Priority**: Must

### FR-8: Built-in Profiles (`generic`, `codex`)
- **Description**: Ship two tested day-one profiles.
- **Acceptance Criteria**:
  - `generic` profile is default and works for Python/Node agents
  - `codex` profile includes Codex CLI-oriented defaults (mount/env/runtime ergonomics)
  - Both profiles pass the same fail-closed and interception E2E suite
- **Priority**: Must

### FR-9: Long-Running Capability Lifecycle Contract
- **Description**: Define behavior for persistent agents without natural session boundaries.
- **Acceptance Criteria**:
  - Capability source supports rotation without process restart (file/command/provider contract)
  - Wrapper reloads capability material before expiry with overlap window
  - On renewal failure past grace window, network remains fail-closed with explicit error reason
  - Behavior is profile-configurable for short-lived vs long-lived agent modes
- **Priority**: Must

### FR-10: Integration Tests and Security Assertions
- **Description**: E2E verification for both profiles and failure modes.
- **Acceptance Criteria**:
  - Tests verify HTTP calls inside sandbox are observed by sidecar
  - Tests verify shell-originated HTTP is mediated
  - Tests verify DENY from sidecar is surfaced as tool/runtime error (not opaque reset)
  - Tests verify sidecar unreachable at startup and mid-session yields zero external egress
- **Priority**: Must

### FR-11: Benchmark Harness and Artifacts
- **Description**: Publish measurable startup and routing overhead for launch narrative.
- **Acceptance Criteria**:
  - Captures `t_backend_ready`, `t_sidecar_ready`, `t_first_request`
  - Captures request latency deltas (baseline vs wrapped) for `generic` and `codex`
  - Emits machine-readable JSON under `target/benchmarks/firma-run/`
  - Emits human-readable summary under `docs/security/` or `docs/architecture/`
- **Priority**: Must

### FR-12: Documentation and Positioning
- **Description**: Explain what FIR-61 does and does not guarantee.
- **Acceptance Criteria**:
  - README includes `firma run` quickstart for generic profile
  - README calls out Linux-only scope for FIR-61 implementation
  - README explains fail-closed behavior and sidecar coverage model
  - FIR-62 separation (Claude Code specifics) is explicit
- **Priority**: Must

## Non-Functional Requirements

### Performance
| Requirement | Metric | Target |
|-------------|--------|--------|
| Sandbox bootstrap latency | `t_backend_ready` p95 | < 350 ms on reference Linux dev host |
| Wrapper+routing startup | `t_first_request` p95 | < 600 ms on reference Linux dev host |
| Added per-request overhead | p95 delta vs direct (HTTP) | < 8 ms |

### Security
| Requirement | Standard | Notes |
|-------------|----------|-------|
| Structural mediation | FIR-60 invariant | No direct external egress path from sandbox |
| DNS confinement | FIR-61 review requirement | Resolver path must be Firma-controlled |
| Fail-closed | FIR-28/FIR-60 alignment | Sidecar unavailable => zero network |
| Deterministic attribution | Audit traceability | Concurrent runs are uniquely attributable |

### Reliability
| Requirement | Metric | Target |
|-------------|--------|--------|
| Wrapper teardown hygiene | Orphan process count | 0 child processes after exit |
| Mid-session sidecar outage handling | Behavior | Calls fail deterministically; no bypass |
| Capability rotation continuity | Renewal success under healthy authority | > 99.9% renewal attempts |

### Usability
| Requirement | Metric | Target |
|-------------|--------|--------|
| First-run success | `firma run -- python ...` without extra setup | Works with documented prerequisites |
| Interactive compatibility | TUI smoke tests pass | 100% for supported terminals in CI baseline |

## Constraints

### Technical Constraints

**Intent-specific constraints**:
- FIR-61 implementation scope is Linux-only; backend contract remains pluggable for FIR-60 matrix continuation.
- Reuse existing crate graph where useful (`firma-sidecar`, `firma-core`, `tonic`, config patterns).
- Bubblewrap and required namespace tooling are runtime dependencies, not vendored binaries.
- Do not introduce a second policy decision plane; sidecar remains enforcement authority.

### Business Constraints
- FIR-61 blocks FIR-62 and is on critical path for launch timeline.
- Claude Code specialization is out of scope in FIR-61.
- Enterprise Firecracker profile is additive, not required for FIR-61 completion.

### Out of Scope
- Full cross-platform backend implementation (macOS/Windows runtime paths)
- Firecracker runtime implementation
- Claude Code-specific orchestration and policy semantics (FIR-62)
- New sidecar policy engine behavior beyond routing/plumbing needs

## Assumptions

| Assumption | Risk if Invalid | Mitigation |
|------------|-----------------|------------|
| `bwrap` is available in target Linux environments | Wrapper cannot start | Add preflight diagnostics + installation guidance + CI coverage |
| Sidecar can be reached over chosen local endpoint model (UDS/TCP bridge) | No traffic mediation | Startup health gate + explicit fallback error + fail-closed |
| Profile defaults cover most generic and codex workflows | Poor first-run UX | Add profile override docs + fixture agents in E2E suite |
| Capability material can be rotated out-of-band for long-running agents | Token expiry causes runtime outages | Define renewal contract in FIR-61 and validate with longevity tests |
